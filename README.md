# 疾控汇总发布安全审查台

疾控数据员在公开「分区 × 年龄组」汇总检出数前，用本工具审查：**多份已公开汇总叠加后，是否会暴露小样本格（原检出数 1~4）的取值**。每次发布同时签发 **HMAC 回执**，外部复核者留存回执即可在日后核验公开记录是否被改动。技术栈：FastAPI + SQLite + z3-solver。

## 快速开始

### Docker Compose（推荐）

```bash
docker compose up --build
```

访问：
- 内部审查台：http://localhost:8000/
- 公开页：http://localhost:8000/public

SQLite 库文件（`/data/app.db`）与回执密钥（`/data/receipt.key`）保存在命名卷 `app_data`，重启后公开记录、签发链与密钥均保留。**请另行备份密钥文件**：密钥丢失且库内已有已签记录时，应用拒绝启动（见「回执与密钥」）。

### 本地运行

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
```

库文件默认在 `./data/app.db`（`DB_PATH` 可覆盖）；回执密钥默认在库文件旁的 `receipt.key`（`RECEIPT_KEY_PATH` 可覆盖）。

### 自测

```bash
.venv/bin/python tests/selftest.py   # 74 项关键功能检查
```

## 演示流程（内置示例数据）

示例数据（`sample_survey.csv`，2 分区 × 2 年龄组，人数均 10）：

| 分区 | 年龄组 | 人数 | 检出数 |
|---|---|---|---|
| 城东 | 青年 | 10 | **2**（受保护小样本格） |
| 城东 | 老年 | 10 | 8 |
| 城西 | 青年 | 10 | 8 |
| 城西 | 老年 | 10 | 8 |

1. 打开内部台 `/`，点「导入示例数据」（导入后不可更换）。
2. 勾选「城东」+ 两个年龄组 → 预览（总数 10，安全）→ 确认发布 → **下载回执 JSON 留存**。
3. 勾选两个分区 +「老年」→ 预览（总数 16）：单独看本安全，但与已发布的「城东」合并后，
   格「城东/青年」被约束到 **[0, 4]**（`城东合计10 − 城东老年≤10 ⇒ 城东青年≤4`，
   且 `老年合计16 ⇒ 城东老年≥6 ⇒ 城东青年≤4`），不再保留「≥5」的可行解 → 审查不通过。
4. 点「确认发布」→ 按最新公开记录重核，返回 409 并列出受影响格与可行范围。
5. 改发「青年」（总数 10）：与已公开记录合并仍安全 → 发布成功，同样签发回执。
6. 打开公开页 `/public`：只有人数表与获准汇总（含回执状态），无格内检出数；
   在「回执核验」框粘贴第 2 步留存的回执 → 显示逐条核验通过、签发链完整。

## 安全模型

- 未知量：每格一个整数 `x_i`，约束**仅**来自
  1. 界限 `0 ≤ x_i ≤ 人数_i`；
  2. 历次公开记录：所选交集格之和 = 公开总数；
  3. 候选发布：所选交集格之和 = 候选总数。
- 判定：对每个原检出数为 1~4 的格，须同时存在 `x_i = 0` 与 `x_i ≥ 5` 的可行整数解，
  否则拒绝并给出该格可行范围（z3 Optimize 求 min/max）。
- 确认发布时在全局发布锁内**重读最新公开记录并重核**，随后单事务写入：
  两个各自安全、合并不安全的窗口不会都被发布；保存失败整体回滚，不留半次发布。
- 求解在工作线程执行（每评估独立 z3 Context，线程安全），求解期间公开页与其他发布可用。

## 回执与密钥

**签发**：每次发布在**同一事务**内完成「插入记录 + 签发回执」——事务（`BEGIN IMMEDIATE`）内
先读前一已签回执、插入记录、按实际 id 计算回执再写回，任一步失败整体回滚，不留单边结果。
回执 = HMAC-SHA256（密钥， 规范序列化（发布ID, 所选范围, 总数, 发布时间, 前一回执摘要）），
各回执经 `prev_receipt` 串联成签发链；写锁自事务开始持有，两窗口同时发布时
**回执顺序与落库顺序一致**。

**留存与下载**：发布后内部台展示回执并提供下载；公开页每条已签记录也有「下载回执」链接
（回执只含公开信息：范围、总数、时间、链上摘要，不含格内检出数）。

**核验**：公开页粘贴回执 JSON → `POST /api/verify`：
1. 回执自身须通过密钥核验（防涂改、防伪造）；
2. 从链首向回执所指记录逐条重算 HMAC 并检查前向链接，报告**首处**（id 最小处）篡改或断链；
3. 回执所指记录须在库中且与回执一致——**末条被删也会报「缺失」，不会误判通过**。

防篡改边界：针对「密钥与用户留存回执未泄露」的数据库改写。攻击者能改库但算不出合法
HMAC，因此改记录、改回执、删中间记录（断链）、删末条（缺失）都会被核验发现。

**密钥管理**：
- 首次启动生成 32 字节随机密钥，以十六进制保存在**数据库之外**的密钥文件
  （默认 `receipt.key`，权限 0600，`RECEIPT_KEY_PATH` 可覆盖），重启沿用同一密钥；
- **密钥丢失且库内已有已签记录 → 应用明确启动失败**（重新生成会让历史回执全部失效并
  掩盖可能的篡改，故必须显式失败，请从备份恢复密钥）；
- 密钥文件损坏（非合法十六进制或长度不足）同样明确失败。

**旧记录**：升级前已存在的发布记录在迁移后 `receipt` 为 NULL，页面与 API 均标为
**未签**，不参与签发链，核验不得判过。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/import` | 导入调查 CSV（multipart，仅一次，导入后不可更换） |
| GET | `/api/admin/state` | 内部状态（含格内检出数） |
| POST | `/api/preview` | `{districts, age_groups}` → 交集总数 + 安全评估 |
| POST | `/api/publish` | 重核后发布并签发回执；不安全返回 409 + 受影响格与可行范围 |
| GET | `/api/public` | 公开数据：仅人数与获准汇总（含回执状态） |
| GET | `/api/receipt/{id}` | 下载已签发布的回执 JSON（未签旧记录返回 409） |
| POST | `/api/verify` | `{receipt_text}` → 逐条核验签发链与库内记录 |

CSV 表头：`分区,年龄组,人数,检出数`（亦兼容 `district,age_group,population,detected`）。
校验：≤16 格；人数 ≥5；检出数为 0~人数整数；（分区,年龄组）唯一。

## 已知限制

- 未实现认证/授权：内部台与接口对任何可达者开放，生产部署须自行加访问控制。
- 发布串行锁为单进程内锁；多副本部署时，`BEGIN IMMEDIATE` 事务已保证回执链与落库顺序
  一致，但「重核-写入」临界区需以数据库级互斥保证（SQLite 单写天然串行）。
- 回执核验防「密钥未泄露的改库」，不防「密钥+回执同时泄露」的重签；密钥文件须按秘密管理。
- 审查基于精确整数可行域（z3），非差分隐私；它保证「小样本格不被公开信息钉死」，不量化其他泄露渠道。
